# План проекта: локальный агент для написания и автотеста Paper-плагинов

Рабочее название: **PlugForge** (не использовать слово «Minecraft» в названии продукта).

---

## 1. Цель и рамки

**Цель:** десктоп-приложение, в котором пользователь описывает плагин обычным текстом, а агент уточняет детали, пишет плагин, сам собирает его, тестирует на настоящем локальном сервере с ботами и исправляет, пока тесты не пройдут. На выходе готовый `.jar`, исходники, отчёт о тестах и папка-заготовка под ассеты.

**Входит в первую версию (MVP):**
- Одна целевая платформа: Paper, одна зафиксированная версия Minecraft, Java 21.
- Подключаемая LLM через OpenAI-совместимый API (по умолчанию DeepSeek, пользователь вставляет свой ключ).
- Уточняющие вопросы, спецификация, генерация кода, сборка, тесты L0–L3, цикл исправлений.
- Ассеты только заглушками (ванильные материалы + манифест + пустая структура resource pack).
- Сначала CLI, затем десктоп-интерфейс поверх того же ядра.

**Не входит (позже или никогда):**
- Сайт, аккаунты, оплата, облачные песочницы.
- Своя обученная модель (данные для неё начинаем копить сразу, см. п. 12).
- Генерация самих текстур, моделей и звуков.
- Несколько версий Minecraft, Fabric/Forge-моды, Velocity/Bungee.
- NMS и работа с пакетами (агент обязан обходиться публичным API Paper).

## 2. Пользовательский сценарий

1. Пользователь устанавливает приложение. При первом запуске оно само скачивает JDK 21, Paper, Gradle-зависимости и Node-рантайм для ботов (если не встроен), затем просит API-ключ модели.
2. Вводит запрос: «Хочу казино: слоты в GUI, ставки на валюту сервера».
3. Агент задаёт 3–7 уточняющих вопросов кнопками или текстом (валюта: Vault или своя? какие игры? шансы? права? команды?).
4. Агент показывает **спецификацию** (команды, права, GUI, конфиг, ассеты, критерии приёмки). Пользователь подтверждает или правит.
5. Агент работает. В интерфейсе видно этапы: код → сборка → юнит-тесты → сервер и боты → исправления (итерация 2/8…).
6. Результат: папка проекта с `.jar`, исходниками, `assets/`, `TEST_REPORT.md`. Кнопка «Доработать» запускает новый запрос поверх существующего плагина.

Как это сделано в CLI сейчас: подтверждение одно — план этапов; спеки этапов агент принимает сам (`--review-specs` вернёт вопрос на каждый этап). В `dist/` рядом с jar лежит полная инструкция (`ИНСТРУКЦИЯ.md`/`MANUAL.md`), написанная по готовому коду. «Доработать» — `improve <папка> "<что добавить>"`: новые этапы строятся поверх готового плагина с той же нумерацией, его тесты и сценарии остаются регрессией, при неудаче проект откатывается к исходному плагину.

### Почему оркестратор — машина состояний, а не свободный агент

Дешёвые модели плохо держат длинные свободные циклы с инструментами: путаются, зацикливаются, забывают цель. Поэтому общий ход работы задаёт код (детерминированные этапы), а LLM вызывается внутри каждого этапа с узкой задачей и ограниченным набором инструментов. Свободный режим с инструментами можно добавить позже для этапа исправлений.

### Состояния оркестратора

```
INTAKE → CLARIFY ⇄ (пользователь) → SPEC → SPEC_APPROVAL ⇄ (пользователь)
  → TESTS_WRITE → CODE_WRITE → BUILD ─fail→ FIX ─→ BUILD
                                 └ok→ UNIT ─fail→ FIX
                                          └ok→ LIVE ─fail→ FIX
                                                   └ok→ ASSETS_CHECK → REPORT → DONE
Лимиты: max_fix_iterations (по умолчанию 8), max_tokens / max_cost на задачу,
таймаут на этап. При исчерпании → STUCK: отчёт что не прошло + вопрос пользователю.
```

## 4. Стек и обоснование

| Часть | Выбор | Почему |
|---|---|---|
| Ядро агента | **TypeScript (Node 20+)** | Mineflayer — Node-библиотека; один язык для ядра, ботов и UI; проще упаковать, чем Python |
| Десктоп | **Electron** | Node уже внутри (нужен для Mineflayer); Tauri потребовал бы отдельный Node-сайдкар |
| UI | React + Vite | Стандартно, быстро |
| LLM | OpenAI-совместимый API; DeepSeek по умолчанию | Смена модели = смена `base_url`/`model` в конфиге |
| Плагины | Java 21, Gradle (wrapper), Paper API | Стандарт экосистемы |
| Юнит-тесты | MockBukkit + JUnit 5 | Готовая «фейковая» реализация Bukkit API |
| Живые тесты | Paper-сервер как обычный java-процесс + Mineflayer | Без Docker: на Windows Docker Desktop — большой барьер для пользователя |
| Проверка состояния сервера | Harness-плагин + RCON | Боты видят только то, что видит игрок; сервер-сайд проверки через свой плагин |
| JDK | Eclipse Temurin 21, скачивается при первом запуске | Не требовать Java от пользователя |
| Хранилище | файлы + SQLite (история прогонов) | Локально, без сервера |

**Версия Minecraft:** на M0 выбрать последнюю версию, которую **одновременно** поддерживают Paper, MockBukkit и Mineflayer (Mineflayer и MockBukkit иногда отстают). Зафиксировать её в одном конфиге `bench.versions.json`.

**Безопасность:** сгенерированный код запускается на машине пользователя. MVP: сервер работает во временной папке, слушает только `127.0.0.1`, `online-mode=false`, рабочая папка удаляется после прогона; статическая проверка кода на запрещённые API (`Runtime.exec`, `ProcessBuilder`, сетевые сокеты, рефлексия в NMS, файловый доступ вне папки плагина), найденное → предупреждение пользователю. Позже: опциональный режим Docker для тех, у кого он есть.

## 5. Спецификация плагина (`spec.json`)

Центральный артефакт. Из неё генерируются и код, и тесты. Пользователь подтверждает именно её.

```jsonc
{
  "name": "SimpleCasino",
  "package": "dev.plugforge.simplecasino",
  "description": "Казино со слотами в GUI на валюту сервера",
  "mcVersion": "<из bench.versions.json>",
  "dependencies": { "hard": ["Vault"], "soft": [] },
  "commands": [
    { "name": "casino", "description": "Открыть казино", "permission": "casino.use",
      "usage": "/casino", "playerOnly": true }
  ],
  "permissions": [ { "node": "casino.use", "default": "true" },
                   { "node": "casino.admin", "default": "op" } ],
  "config": [ { "key": "slots.min-bet", "type": "double", "default": 10 } ],
  "guis": [
    { "id": "main", "title": "Казино", "rows": 3,
      "slots": [ { "slot": 13, "item": "casino:slot_machine", "action": "open:slots" } ] }
  ],
  "events": [ ],
  "persistence": "yaml",           // none | yaml | sqlite
  "messages": { "notEnoughMoney": "&cНедостаточно средств" },
  "assets": [
    { "id": "casino:slot_machine", "kind": "item_icon", "fallback": "GOLD_BLOCK",
      "size": "16x16", "usedIn": "gui main slot 13" }
  ],
  "acceptance": [
    { "id": "AC1", "text": "Игрок с правом casino.use по /casino видит GUI «Казино»" },
    { "id": "AC2", "text": "При ставке больше баланса — сообщение notEnoughMoney, баланс не меняется" },
    { "id": "AC3", "text": "Игрок без права получает отказ" }
  ]
}
```

Каждый пункт `acceptance` обязан быть покрыт хотя бы одним тестом L1 или L2. Это проверяет код оркестратора, а не LLM.

## 6. Этапы агента подробно

### 6.1 Clarifier
- Вход: запрос пользователя + чек-лист «что обычно нужно знать» (команды, права, хранение данных, экономика, GUI, конфиг, сообщения и язык, ассеты).
- Выход: список вопросов с вариантами ответов (для кнопок в UI) **или** «уточнения не нужны».
- Не более 2 раундов; на остальное агент берёт разумные значения по умолчанию и явно пишет их в спеку.

### 6.2 SpecWriter
- Генерирует `spec.json` по JSON Schema; невалидный ответ → повтор с ошибкой валидации.
- Пользователь видит спеку в читаемом виде и может править.

### 6.3 TestWriter (до кода!)
- Генерирует MockBukkit-тесты и YAML-сценарии L2 по `acceptance`.
- **Coder и Fixer не имеют права менять тесты.** Иначе модель «чинит» тесты под сломанный код. Если Fixer считает тест ошибочным, он помечает это, и оркестратор отправляет тест на отдельную проверку (TestReview) с объяснением.

### 6.4 Coder
- Генерирует проект по шаблону (`templates/paper-plugin/`): `build.gradle.kts`, `plugin.yml`/`paper-plugin.yml`, главный класс, пакеты `command/`, `listener/`, `gui/`, `config/`, `asset/`.
- Работает пофайлово: сначала план файлов (список + назначение), затем каждый файл отдельным вызовом. Так дешёвые модели ошибаются реже, чем при генерации всего сразу.
- В контекст подаются: спека, план файлов, шпаргалка по нужным частям Paper API (из Knowledge по ключевым словам спеки).

### 6.5 Fixer
- Вход: компактная выжимка ошибки (не весь лог): ошибки компилятора с файлом и строкой, упавший тест с assertion, стектрейс сервера, шаги сценария до падения.
- Выход: патчи в формате search/replace по файлам.
- Защита от зацикливания: если та же ошибка повторилась 3 раза → эскалация (другой промпт, более сильная модель из роутинга или STUCK).

### 6.6 Reporter
- `TEST_REPORT.md`: что проверено, по каждому AC статус и тест, число итераций, токены и стоимость, предупреждения статической проверки, список ассетов-заглушек.

## 7. Тест-стенд

### L0 — Build
- `gradlew build -x test` в изолированной папке с общим кешем Gradle (`%APPDATA%/PlugForge/gradle-cache`) — после первого запуска собирается офлайн.
- Валидация `plugin.yml`: команды и права из спеки присутствуют, `api-version` верный, главный класс существует.
- Статическая проверка запрещённых API.

### L1 — Unit (MockBukkit)
- `gradlew test`, парсинг JUnit XML → структурированный результат для Fixer.
- Для Vault-зависимых плагинов: мок экономики в тестовых утилитах шаблона.

### L2 — Live (Paper + боты)
- **Сервер:** заготовленный «чистый» шаблон мира (плоский, маленький, предгенерированный) копируется во временную папку → быстрый старт. В `plugins/` кладутся: тестируемый плагин, harness-плагин, зависимости из спеки (Vault + простая экономика-заглушка из каталога).
- **Harness-плагин** (наш, пишется один раз): HTTP/сокет на localhost. Даёт команды для тестов: выдать или забрать деньги, поставить блок, телепортировать, прочитать баланс и инвентарь, прочитать блок, перехватить исключения плагина в логах, «тикнуть» N тиков.
- **Боты (Mineflayer):** заходят как `player1..N`, выполняют шаги сценария.
- **Сценарий (YAML):**

```yaml
id: AC2_not_enough_money
covers: [AC2]
players: [player1]
setup:
  - harness: { setBalance: { player: player1, amount: 5 } }
  - harness: { grantPermission: { player: player1, node: casino.use } }
steps:
  - as: player1
    command: /casino
  - expect_gui: { title_contains: "Казино" }
  - click_slot: 13
  - expect_gui: { title_contains: "Слоты" }
  - click_slot: 11            # кнопка ставки
  - expect_chat: { contains: "Недостаточно средств" }
  - harness_expect: { balance: { player: player1, equals: 5 } }
  - expect_no_errors: true      # в логе сервера нет исключений от плагина
```

- Набор шагов DSL расширяется по мере надобности: `chat`, `command`, `click_slot`, `close_gui`, `place_block`, `break_block`, `use_item`, `move_to`, `wait_ticks`, `expect_*`, `harness`, `harness_expect`.
- Сервер один на весь прогон L2 (между сценариями сброс состояния через harness), перезапуск только при падении.

### L3 — Assets
- Каждый `asset.id` из спеки встречается в коде (через реестр `Assets.java`), и наоборот, в коде нет незаявленных ключей.
- `assets/` содержит корректную структуру пака и валидный `pack.mcmeta`.

## 8. Ассеты-заглушки

Агент ассеты не рисует. Он оставляет под них готовые места:

```
<plugin-project>/
  assets/
    manifest.json                 # что нужно нарисовать: id, тип, размер, где используется, fallback
    README.md                     # инструкция для художника
    resourcepack/
      pack.mcmeta
      assets/<namespace>/
        textures/item/            # пусто, сюда класть PNG
        models/item/              # заготовки JSON моделей, ссылаются на текстуры
        items/                    # item model definitions (для новых версий)
```

- В коде предмет создаётся через единый реестр `Assets.item("casino:slot_machine")`, который ставит ванильный материал-заглушку + ключ модели (`item_model` или `CustomModelData` в зависимости от версии).
- Когда пак положат на сервер, подменится только визуал, код не меняется.

## 9. LLM Gateway

- Конфиг профилей:

```jsonc
{
  "profiles": {
    "cheap":  { "baseUrl": "https://api.deepseek.com", "model": "deepseek-flash", "apiKeyRef": "deepseek" },
    "strong": { "baseUrl": "...", "model": "...", "apiKeyRef": "..." }
  },
  "routing": {
    "clarify": "cheap", "spec": "cheap", "tests": "cheap",
    "code": "cheap", "fix": "cheap", "fix_escalation": "strong"
  },
  "budget": { "maxCostUsdPerTask": 0.5 }
}
```

- Ключи хранятся в системном хранилище (Windows Credential Manager через `keytar`/`safeStorage` Electron), не в открытом виде.
- Учёт токенов и стоимости по каждому вызову.
- Ретраи, таймауты, обработка перегрузки API.
- Работа с локальными моделями (Ollama, vLLM, LM Studio) — тот же OpenAI-совместимый интерфейс.

## 10. Knowledge (без обучения модели)

- `knowledge/paper-api/*.md` — короткие шпаргалки по темам: команды (Brigadier и классические), события, GUI-инвентари, PDC, конфиги, планировщик, Adventure-компоненты, Vault, права, сохранение данных, частые ошибки.
- Подбираются в промпт по ключевым словам спеки (на старте простое сопоставление по тегам, векторный поиск только если понадобится).
- `knowledge/examples/` — 10–20 эталонных мини-плагинов, написанных и проверенных вручную на нашем стенде.
- Список «не делай так»: устаревшие API, `ChatColor` вместо Adventure, синхронные операции с БД в главном потоке и т. п.

## 12. Данные для будущей своей модели (собираем с первого дня)

Каждый прогон пишется в `runs/<id>/`: запрос, вопросы и ответы, спека, все версии кода по итерациям, все ошибки, итоговый статус тестов, модель, токены. Это бесплатно копит пары «запрос → рабочий плагин» и «ошибка → исправление» — лучший материал для будущего дообучения. Отправка этих данных разработчику — только с явного согласия пользователя (opt-in).

## 13. Этапы разработки (milestones)

Каждый этап заканчивается проверяемым критерием готовности.

| # | Этап | Что делаем | Готово, когда |
|---|---|---|---|
| **M0** | Фундамент стенда | Monorepo; выбор и фиксация версий; Runtime Manager скачивает JDK, Paper; запуск и остановка сервера из Node; бот Mineflayer заходит и пишет в чат; RCON | Одна команда CLI поднимает сервер, бот заходит, пишет «hello», сервер гасится, папка чистится |
| **M1** | Шаблон и L0/L1 | Шаблон Paper-плагина с MockBukkit; сборка и тесты из Node; парсинг ошибок компиляции и JUnit XML | Ручной плагин из шаблона собирается и проходит тесты; сломанный — даёт структурированную ошибку |

Порядок важен: M0–M4 — это ценность продукта (агент реально проверяет плагины). UI (M7) строится, когда ядро уже работает и измерено на бенчмарке.

## 14. Метрики

- **Solve rate** на бенчмарке (все скрытые тесты зелёные), отдельно по сложности.
- Среднее число итераций исправления.
- Стоимость и время на задачу.
- Доля «нечестных» решений: прошли наши тесты, но упали на скрытых (показывает, насколько хорошо TestWriter покрывает спеку).

## 15. Риски и что с ними делаем

| Риск | Меры |
|---|---|
| Дешёвая модель плохо пишет многофайловый Java | Пофайловая генерация, шаблон, шпаргалки, эталонные примеры, эскалация на сильную модель |
| Модель подгоняет тесты под код | Тесты пишутся до кода и заблокированы для Coder/Fixer; скрытые тесты в бенчмарке |
| Нестабильные (flaky) L2-тесты | Ожидания по событиям, а не по таймерам; повтор упавшего сценария 1 раз; детерминированный мир |
| Mineflayer/MockBukkit отстают от свежей версии MC | Фиксируем версию, которую поддерживают все три; обновление версии — отдельная задача |
| Первая сборка медленная (загрузка зависимостей) | Прогрев кеша Gradle при первом запуске приложения |
| Опасный сгенерированный код на машине пользователя | Только localhost, временные папки, статическая проверка API, предупреждения; опциональный Docker позже |
| Плагину нужна сторонняя зависимость, которой нет в каталоге | Каталог расширяется вручную; при отсутствии — предупреждение и тесты только L1 с моками |
| Расходы пользователя на API | Бюджет на задачу, показ стоимости, поддержка локальных моделей |

## 16. Открытые вопросы (решить до или во время M0)

1. ~~Целевая версия Minecraft и Paper~~ — **решено на M0:** 1.21.11, Paper build 132, Java 21, Mineflayer 4.39.0, MockBukkit `mockbukkit-v1.21` 4.116.3 (см. `bench.versions.json`). Серия 26.x пока не подходит: Mineflayer тестирует только до 26.1, MockBukkit для 26.1 нет.
2. ~~`plugin.yml` или `paper-plugin.yml`~~ — **решено на M1:** `plugin.yml` (команды объявляются в нём, MockBukkit полностью поддерживает). Важно для промптов: главный класс плагина не должен быть `final` — MockBukkit 4 грузит плагин через сгенерированный подкласс.
3. ~~Команды: `CommandExecutor` или Brigadier~~ — **решено на M2:** классический `CommandExecutor` + команды в `plugin.yml`. Модели пишут его надёжнее, MockBukkit полностью поддерживает `performCommand`. К Brigadier можно вернуться позже как к опции.
4. Язык интерфейса и сообщений плагинов по умолчанию (RU/EN).
5. Лицензия проекта, если будет открытым.
